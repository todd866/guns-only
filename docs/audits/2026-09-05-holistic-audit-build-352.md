# Guns Only: holistic audit of Build 352

Audit date: 5 September 2026. Public build: **352**, revision **1ed5488d0271aad87118fa8c64eb9dcbd0d50c79**, deployment **dpl_HH3BDp5QFjMzvp9NYLYoKe7rLLEM**. Verified from the public build endpoint and visible application identity. Source links below are pinned to that revision.

**My assessment: the simulation has more depth than the surrounding product consistently helps a player use.** Guns Only has valuable foundations: deterministic authority, physically consequential actions, sourced aircraft models, replay evidence, a distinctive setting, and serious release safeguards. The next substantial improvement should make that depth understandable, repeatable, and reliably playable across the existing six programmes.

Builds 344–352 already addressed many earlier weaknesses. Shared lifecycle and exit flows exist; Cobra has an authored battle and recovery; Top Gun has a finite fight and carrier return; Fire Boss has a meaningful scoop/drop/recovery loop; the first F-22 visit has a guided valley. Recommending those features as if they were missing would waste work. The remaining task is to prove, simplify, and connect them.

**Scope and confidence.** I reviewed the production source, architecture and status documents, release workflow, representative simulation and presentation paths, input/onboarding/progression, performance and AI harnesses, telemetry endpoints, and presence/arena boundaries. I inspected the public desktop selector, F-22 fight, explicit first-run valley, Cobra brief/start/pause, and Fire Boss briefing, and sampled Weekend Ride’s entry. Browser work was silent, with shared presence disabled. This was not six complete human acceptance sorties, an audio listening session, a penetration test, or a hardware FPS benchmark. The attempted phone viewport override remained 1280 × 720, so no new phone-layout acceptance is claimed.

The initial working directory was on an older dirty branch at `838bd666`. I switched the audit to the clean production checkout at `.worktrees/deepdive-346`, which remained at `1ed5488d` without tracked changes. This report is the only authored repository file; no game changes, pushes, or deployments were made.

**Verification completed.** The exact deployed revision has a successful [Verify run](https://github.com/todd866/guns-only/actions/runs/33845408252). Locally, **585 selected JavaScript tests passed**, spanning progression, release, input, onboarding, APIs, release tooling and performance-harness contracts. **156 selected C# tests passed**, covering snapshot parity, first-run valley, Cobra missions, Okanagan and Top Gun carrier RTB. The ordinary .NET test host could not bind its sandboxed socket; the repository’s supported in-process runner completed successfully. NuGet vulnerability metadata was unavailable in the restricted environment, so these checks do not constitute a fresh dependency vulnerability scan. I did not repeat the complete release gate or fly the full autonomous mission suite.

**1. Acceptance is the largest immediate risk.** CI verifies substantial unit, content, published-browser and HUD behavior. It does not run the full autonomous mission suite, the actual scenery capture/scoring pass, or a real-GPU performance matrix. `bin/check` explicitly says that visual scorer tests captured no frames. The current status document also says the F-22 player-AI gate is not release-qualified and has not fired a production round. That refers to the automated player, not a claim that the current enemy never fires. Build 351 specifically repaired an enemy presentation-state issue.

There is a further distinction inside the autonomous suite: its Cobra registration selects `goal: "engage"`, and Weekend selects `goal: "lap"`. Those are useful behavior checks, but they do not certify Cobra’s complete battle-to-recovery or Weekend’s end/debrief/retry lifecycle. “A driver exists” and “the whole player contract passed on this build” need separate status.

Preserve the current fast checks. Add a release evidence manifest keyed by commit, content digest, route, device/input profile and scenario seed. Record separate results for launch, meaningful action, outcome, recovery, debrief/retry, visuals, performance and human acceptance. Unrun checks should remain visibly unrun. Require the relevant slices for a changed production mode; keep explicit owner-directed release exceptions reviewable. Do not make the still-unqualified AI pilot a blanket release blocker until it earns that role.

For F-22, first qualify one reproducible contested fight: real production input, a valid firing opportunity, ammunition expenditure, physical weapon evidence, and an interpretable outcome. Separate “the controller could not fly it” from “the game contract failed.” Grow the seed/device matrix only after this basic sample is dependable. Human novice observations are also necessary: an autopilot cannot establish that a briefing is understandable or a fight enjoyable.

**2. The first sortie asks a newcomer to learn several difficult skills in one chain.** The current first-run brief asks for low-level valley flight, a pop-out, two missiles, a transition to guns, two kills and runway recovery. The controls and next-action strip are now explicit, which is good. The unresolved product question is whether a new player can earn an intelligible success before becoming overloaded. I did not measure novice success rates, so this is a usability hypothesis to test, not a demonstrated retention failure.

Use the existing authoritative procedure gates to recognize intermediate accomplishments. A player should know that they flew the valley correctly even if they later lose the fight. Offer deliberate practice of the failed phase as a separately identified training scenario; keep a complete sortie’s outcome truthful. Let a player repeat an approach, track a target, or practice a scoop without paying the full preceding journey every time.

The highest-value small additions would be an actionable control hint at the moment it is needed, a clear distinction between practice and complete sorties, and a debrief that connects one observed mistake to one next attempt. Avoid forcing the player through additional reading. Test this with several people unfamiliar with the game and observe time to deliberate control, first meaningful success, confusion, exit, and voluntary retry. Prefer observed sessions and local evidence over adding central gameplay collection by default.

One testing hazard deserves attention: `shouldAutoStartFirstRunValley` deliberately chooses a different default when `navigator.webdriver` is true. Existing smoke explicitly exercises `?firstRun=1`, so the intro is not untested. However, a generic automated root-page visit is not evidence of the real first-visit route. Move test routing into explicit test inputs where practical and retain a fresh-storage default-route acceptance case.

**3. Spend the next visual pass on legibility and coherence.** In the live F-22 scene, thin pale-green pitch/heading markings and small instrument text were difficult to distinguish against bright cloud and sky. Cobra had the same contrast tendency. Selected target labels and the dark objective blocks were easier to read. This is a visual observation, not a formal contrast measurement or a judgment about all weather conditions.

Give essential flight and weapon cues a consistent dark halo or backing, a minimum readable stroke/text size, and a restrained priority system. Add shape or wording to energy guidance so green/yellow/red is not the only signal. Judge it using actual player views toward sun, cloud, terrain, water and dusk, at desktop and phone sizes. Screenshot assertions should protect cue visibility and useful scene composition as well as geometry.

The public presentation still varies between the main poster picker, gold/serif Cobra and valley briefs, and the brighter green/sans Fire Boss menu. Return actions also vary between “Choose sortie,” “Choose another mission,” and “Aircraft.” Some difference suits each aircraft’s character, but navigation, primary-action hierarchy, pause/help discovery and typography should feel like one application. Reuse the existing shell work rather than introducing another design layer. In the inspected desktop Cobra flight, H/Controls was exposed while pause depended on Escape; the main shell and Fire Boss expose visible pause buttons. Make those essential actions consistently discoverable.

For scenery, concentrate on silhouettes, depth, landmarks and material scale from the cockpit. The Cobra firebase read as strongly geometric structures against much denser vegetation and a softer sky. Better integration would help more than uniformly increasing prop counts. Audio now has substantial causal/profile-specific implementation; retain that work and evaluate mix priorities in a separate explicitly audible acceptance session. This silent audit cannot judge sound quality.

**5. Startup and performance need budgets tied to real devices and phases.** Static import traversal from `app.js` reached **159 local JavaScript files totaling 4,284,382 uncompressed bytes**, including vendored Three.js but excluding WASM, terrain, textures and audio. This is a source graph measurement, not the compressed network transfer or an observed loading duration. It shows a worthwhile target for measurement: a player pays to load substantial shared and optional code before the selected experience is ready.

Measure cold and warm start separately, then split optional mission presentation and authoring/preview dependencies from the selected route. Evaluate a small production bundling/content-hash step to reduce the many module requests and manual version propagation. Preserve the strong existing stale-build and service-worker checks. Do not assume bundling alone fixes terrain preparation or WASM startup.

The existing foreground performance contract is useful: at least 59 FPS, p95 at most 18.5 ms, p99 at most 22 ms, no more than 3% of frames over 18.5 ms, and a separate 100 ms catastrophic-hitch limit. Apply it to representative sustained flight and battle, with the actual renderer and input device recorded. Define appropriate supported-device tiers rather than claiming every device meets the desktop target. Include cold start, terrain streaming, firing/effects, return approach, repeated restarts, background/resume and thermal/long-session behavior. Keep SwiftShader results classified as CPU-hitch evidence.

The hot/cold snapshot transport is already a significant optimization. Avoid proposing a new binary bridge as if it did not exist. Profile its cold-version invalidation frequency, allocation rate, copying and JSON fallback before further transport changes. The current five-second fallback makes correctness depend heavily on complete cold-field invalidation.

**6. The architecture is sound at its boundaries and expensive at its centers.** The production tree contains 2,002 tracked files and about 379,218 C#/JavaScript lines including tests, excluding vendor/lib trees. These figures indicate review surface, not quality or test coverage. Important concentrations are:

| File | Lines | Why it matters |
| --- | ---: | --- |
| `web/wwwroot/app.js` | 12,008 | Routing, lifecycle, input, telemetry, rendering and UI share one change surface |
| `sim/SimulationSession.cs` | 8,539 | Mission-specific decisions accumulate in the central authority coordinator |
| `web/wwwroot/hud.js` | 5,914 | Shared symbology and mission-specific presentation are difficult to review independently |
| `web/SnapshotHotFrame.cs` | 3,014 | Projection and invalidation must remain consistent with the JSON contract |
| `tools/perf/fixed_wing_ai_pilot.mjs` | 9,149 | Acceptance tooling is itself a substantial control system |
| Its corresponding test file | 11,644 | The evaluator now has a large maintenance and review burden of its own |

Extract around responsibilities that already exist: mission selection/lifecycle, browser services, vehicle/mission presentation and their teardown. Keep `SimulationSession` as the public coordinator while moving bounded mission rules into existing or focused runtimes. Avoid an engine rewrite or generic ECS migration without a demonstrated need.

Define snapshot fields, units, optionality and update ownership once, then derive the JSON and hot-buffer projections where practical. Retain the existing parity tests and add coverage that verifies cold-only state transitions invalidate the snapshot immediately. Source-regex wiring tests can remain cheap tripwires, but they should not be the sole proof that a player action changes authority and produces the correct visible result.

Two additional targeted checks belong here: browser back/forward-cache restoration after `pagehide` teardown, and WebGL context-loss recovery. The inspected Back navigation performed a fresh load, so I did not reproduce a cached-page failure. Source nevertheless contains unconditional teardown and little restoration machinery in standalone routes; treat this as a test target, not a confirmed live bug. Also add the arena Worker and ASP.NET parity suites to a named gate before that preview grows: they are not referenced in the current main solution/check workflow, though the Vercel arena API does have gated tests.

**7. Connect practice before expanding the world.** The Cohort direction is compelling, but the current public offering is six largely separate programmes. The old qualification functions intentionally became no-ops; a missing global mastery system is therefore not an accidental regression. A useful next layer is a local logbook of actual attempts: aircraft, scenario/version, conditions, outcome, recovery, one evidence-backed correction, and whether the next attempt improved that dimension. Weekend’s persistent lap best is a good existing example of a reason to return.

Keep aircraft access independent of this record. Do not introduce arbitrary XP or physics buffs. Add export/import and deliberate sharing when useful. Then prove one small connection in the world: a named place or crew that remembers an outcome, or a modest logistics/recovery consequence feeding a subsequent sortie. A bounded shared-world slice would advance the stated ambition more convincingly than another disconnected vehicle or an early generic authoring platform.

For future contributors, ship one exemplary scenario that can be changed, validated, run and debriefed without touching the main application or simulation coordinator. The repository already has an MIT license, schemas, provenance and tooling; the missing opportunity is a short, demonstrated authoring path.

**8. Preserve the security and delivery safeguards; verify their operational assumptions.** Same-origin checks, bounded request bodies, private immutable telemetry chunks, separate raw/report credentials, fail-closed preview storage, content digests, exact-revision CI provenance and automatic rollback are valuable. Presence explicitly marks client poses as non-combat authority; the rated ladder is documented as a soft client-reported system. Do not promote either into a competitive authority claim. The world service’s 64-client ceiling is a declared limit, not evidence of large-world scalability.

A scoped independent Cursor/Gemini review of eleven hosted/release files found no material high-impact defect in that scope. I rejected its suggested expired-rate-bucket bug: the implementation does evict expired entries before rejecting a new principal. Its discussion of local arena fallback and client-authoritative presence described documented design choices, not new defects.

Remaining operational questions are evidence gaps: is the documented authoritative Vercel Firewall rule enabled, what are actual spend/retention limits, and can an operator exercise the kill switch and rollback procedure? I did not inspect private deployment settings or collect player records. Record those answers once in a bounded operational check. The current CSP only restricts framing; a compatible script/resource policy can be evaluated as defense in depth, with WASM/worker compatibility tested, rather than reported as an observed exploit.

Make clean-clone setup reproducible as well. The normal shell here selected Node 20 while CI requires 24; the correct runtime was installed and used for the audit. Worktree hydration also depends on an already hydrated local source, while CI downloads verified atlas content from production. Provide a documented public bootstrap and an immutable artifact source so a new contributor or disaster-recovery checkout does not depend on this workstation or the current public deployment remaining available.
